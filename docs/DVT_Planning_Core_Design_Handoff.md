# BẢNG ĐIỀU HÀNH DVT
## Planning Core Design Handoff for Implementation

**Purpose:** Implementation-ready handoff specification for Claude / development team.  
**Scope:** Core Planning design decisions finalized in review.  
**Status:** Approved design baseline.  
**Language convention:** Business/UI labels may be Vietnamese; technical names use English where useful.

# 1. Scope

This document defines the approved core design for the DVT Planning module, including:

- Edit Mode and exclusive editing session
- Frontend Draft State
- Virtual Sequence and drag/drop behavior
- Undo / Redo / Revert
- Formula Definition and dependency handling
- Manual override behavior
- Recheck / validation / commit gate
- Working Calendar at day level
- Multi-line planning and line transfer
- Planning versioning / issue / compare
- Actual mapping and ERP/eGMF synchronization
- Sync Log and Dashboard notifications
- Actual history / snapshot
- Retention / archive / year-end carry-forward
- Production completion baseline

Detailed milestone/status design and time-of-day calendar handling are intentionally deferred.

# 2. Core Principles

## 2.1 Single writer, multiple readers

At any time, only **one active `EditSessionId`** is allowed to modify Planning.

- User enters Edit Mode.
- Backend creates a unique `EditSessionId`.
- Only requests carrying the active valid `EditSessionId` may perform editing/commit-related operations.
- All other users remain in View Mode.
- `EditSessionId` is issued by backend, never self-generated by frontend.
- An expired/closed/revoked `EditSessionId` can never be reused.

Recommended session states:

```text
ACTIVE
CLOSED
EXPIRED
REVOKED
```

Recommended lock/session fields:

```text
EditSessionId
UserId
StartedAt
LastHeartbeat
Status
```

Lock release conditions:

- Commit / Save finished
- Cancel Edit
- Session timeout after heartbeat loss
- Admin Force Unlock

Backend must validate `EditSessionId` again on write/commit APIs.

---

## 2.2 Planning editing is draft-first

During Edit Mode, frontend works on a local **Draft State**, not by writing every drag/drop directly to PostgreSQL.

High-level flow:

```text
Load current plan
→ Enter Edit Mode
→ Create local Draft State
→ User edits / drags / merges / splits / transfers
→ Recheck All Plan
→ Fix issues if needed
→ Recheck PASS
→ Commit
```

The objective is spreadsheet-like interaction.

# 4. Virtual Sequence

## 4.1 Purpose

Every row currently visible/active in Edit Mode must have a temporary frontend position:

```text
virtualSequence
```

This is required for:

- reorder
- insert from Unplanned
- merge
- split
- current draft ordering
- runtime `PREVIOUS_SEQUENCE` resolution

`virtualSequence` is not the row identity.

Immutable identity and position must be separated:

```text
rowId             = immutable identity
virtualSequence   = frontend temporary position
sequenceKey       = backend persisted business order after commit if needed
```

---

## 4.2 Reindexing rule

After every structural action that changes ordering:

- reorder
- add from Unplanned
- merge
- split
- move between line/group when it changes order

frontend must:

```text
Lock Planning UI
→ Rebuild virtualSequence
→ Validate
→ Commit sequence into Draft State atomically
→ Increment SequenceRevision
→ Unlock UI
```

The next action is allowed only if virtual sequence update succeeds.

Validation must ensure:

- no duplicate `virtualSequence`
- no missing active row
- every active row has a sequence
- no two active rows occupy same position
- array order matches `virtualSequence`
- merged hidden source rows do not participate in active ordering
- newly created draft rows have valid position

Performance requirement:

```text
Target: < 100 ms
Acceptable: < 300 ms
Hard UX limit: < 500 ms
```

Virtual reindexing is frontend-only and must not require backend roundtrip.

---

## 4.3 SequenceRevision

Every successful structural reindex increments:

```text
SequenceRevision++
```

Any formula result based on an older sequence revision must be discarded if a newer sequence revision exists.

This prevents race conditions where recalculation finishes using stale row order.

# 5. Undo / Redo / Revert

## 5.1 Spreadsheet-like behavior

Support:

```text
Ctrl + Z            Undo
Ctrl + Y            Redo
Ctrl + Shift + Z    Redo
Revert All Changes
```

Recommended maximum:

```text
100 actions per Edit Session
```

Undo/Redo history only exists inside the active edit session.

Reset history when:

- Commit
- Cancel Edit
- switch to another Planning Version
- session is replaced

---

## 5.2 Action-history approach

Do not rely only on `hidden` state.

Use:

```text
Draft State
+
Undo/Redo Action History
```

Suggested actions:

```text
MOVE
ADD_FROM_UNPLANNED
MERGE
SPLIT
EDIT_FIELD
RETURN_TO_AUTO_CALC
LINE_TRANSFER
```

Example merge history:

```text
MERGE
sourceRows: [B, C]
sourcePositions: [4, 5]
createdRow: M
createdPosition: 4
```

`hiddenByMerge` may be used in current state, but Undo must use action history to restore exact prior state.

# 6. Add from Unplanned

Dragging an item from Unplanned to Planned is not only reordering.

Frontend creates a new temporary draft row:

```text
tempRowId
sourceId
lineId
virtualSequence
status = DRAFT_NEW
```

Cancel removes the temporary row and returns the source item to Unplanned.

Only Commit creates/persists the final backend Planning row.

---

# 7. Merge / Split

## 7.1 Merge

Merge in frontend Draft is reversible.

Do not destroy source row identity.

Example:

```text
B + C → M
```

Draft keeps:

```text
M.mergeSources = [B, C]
B.hiddenByMerge = true
C.hiddenByMerge = true
```

Undo:

- remove M
- restore B/C
- restore original positions

After Commit, ordinary Ctrl+Z no longer applies.

If future business requires reversing a committed merge, use a separate controlled Unmerge/Split function.

## 8.1 Column Formula Definition

Formula definition is configured by Planning column.

Recommended UI structure:

```text

Input Type
List Source
Formula
Sample Result
```

Possible input types:

```text

```

For `Select from List`, use business/master sources such as:

```text
Factory

Customer
Style
Model
Season
Sport
Worker Group

```

Do not expose physical DB table names to business users.

---

## 8.2 Dependency metadata

`Column Formula Definition` is the source of dependency metadata.

Example:

```text
TOTAL_DAY = QUANTITY / CAPACITY
```

System derives:

```text
TOTAL_DAY depends on:
QUANTITY
CAPACITY
```

Dynamic cross-row example:

```text
BEGIN_PROD_DATE =
PREVIOUS_SEQUENCE.END_PROD_DATE + 1 Working Day
```

Dependency template:

```text
ReferenceType = PREVIOUS_SEQUENCE
SourceColumn = END_PROD_DATE
Calendar dependency = Working Calendar
```

Architecture:

```text
Column Formula Definition
→ Dependency Template
→ Runtime Cell Dependency
```

Do not persist every physical cell-to-cell dependency in DB in advance.

---

## 8.3 Circular dependency

At formula definition save/publish:

```text
Syntax validation
Field/reference validation
Type validation
Circular dependency validation
Test/Preview
Publish
```

Example invalid configuration:

```text
A = B + 1
B = C + 1
C = A + 1
```

Must be rejected before Publish.

Runtime still needs a lightweight loop guard for dynamic references such as `PREVIOUS_SEQUENCE`, to protect against corrupted data or resolver bugs.

# 9. Calculated Cell Override

A calculated cell may be manually changed.

When changed:

```text
ValueSource = OVERRIDE
```

UI behavior:

- orange highlight/border
- show `!`
- formula remains preserved internally

Cell state:

```text
CalculatedValue
OverrideValue
EffectiveValue
```

Rule:

```text
EffectiveValue =
  OverrideValue, if OVERRIDE
  otherwise CalculatedValue
```

All downstream formulas use `EffectiveValue`.

Right-click / action:

```text
Return to Auto Calculate
```

When selected:

```text
ValueSource = CALCULATED
OverrideValue = null
DisplayedValue = current CalculatedValue
```

The `!` disappears.

If later inputs change and auto result differs from the current fixed planning value, keep the planning value and show `!`; do not silently change the plan.

# 10. Recalculation Strategy

Initial design:

- dependency-driven auto calculation
- only affected downstream cells are recalculated
- do not recalculate the whole plan after every small change

However, real-world performance must be tested.

Fallback if runtime becomes slow:

```text
Edit freely
→ only lightweight/local auto calculation
→ deeper dependencies marked Needs Recheck
→ user clicks Recheck All Plan
→ full calculation + validation
→ PASS required before Commit
```

`Recheck` scope is:

```text
ALL PLAN ONLY
```

Not selected cells/rows/lines.

---

# 11. Recheck All Plan

Recheck is the final full-plan calculation and validation step.

Recommended checks:

```text
Formula recalculation
Dependency validation
Virtual/business sequence validation
Calendar validation
Line availability
Capacity checks where defined
Transfer validation
Mapping-related validation where relevant
```

Result levels:

```text
PASS
WARNING
ERROR
```

Commit gate:

- `ERROR` → Commit disabled
- `PASS` → Commit allowed
- `WARNING` → business rule may allow commit; default design may permit warning-only commit if approved

Recheck result is tied to the exact `DraftRevision`.

If user edits anything after a successful Recheck:

```text
ValidationState = Needs Recheck
```

and Commit becomes unavailable until Recheck succeeds again.

Each Recheck should have:

```text
CalculationTraceId
DraftRevision
StartedAt
CompletedAt
Result
```

# 14. Offline / Wi-Fi Loss

If Wi-Fi is lost during Edit Mode:

```text
Frontend → OFFLINE
Keep Draft State
Keep Undo/Redo
Keep Virtual Sequence
Disable Commit
Disable Recheck
```

Frontend may continue local editing.

Store local draft periodically in browser persistent storage such as IndexedDB so browser crash/reload can recover.

When network returns:

```text
Check active EditSessionId
```

Case A: session still ACTIVE

```text
continue editing
→ Recheck All Plan
→ Commit if PASS
```

Case B: session EXPIRED

```text
preserve local draft
do not auto-write it to backend
user reacquires Edit Mode
restore local draft into new session
→ Recheck All Plan
→ Commit if PASS
```

UI should offer:

```text
Recover unsaved planning draft?
```

A heartbeat grace period should be used so short network loss does not immediately release the lock.

# 15. Working Calendar

## 15.1 Current scope

Calendar is day-level only.

Deferred to later:

- morning / afternoon / evening
- custom time ranges
- working minutes
- WorkingFraction
- CapacityFactor

Current calendar statuses:

```text
WORKING
OFF
OVERTIME
```

---

## 15.2 Calendar hierarchy

Calendar inheritance:

```text
Company
→ Xí nghiệp
→ Production Line
```

Priority:

```text
Production Line > Xí nghiệp > Company
```

The smallest/most specific scope wins.

Example:

```text
Company: Sunday = OFF
XN1: 20/09 = OVERTIME
Line 7: 20/09 = OFF
```

Resolved:

```text
Line 7 = OFF
Other XN1 lines = WORKING
```

---

## 15.3 Company calendar rule types

At Company level support:

```text
1. Weekly Off Rule
   Example: Sunday

2. Date-specific Off
   Example: public holiday

3. Overtime / Extra Working Day
   Example: a normally-off Sunday becomes working
```

XN may add XN-wide OFF/OVERTIME.

Line may add Line-specific OFF/OVERTIME.

Do not physically copy Company calendar records into every XN.

Use inheritance + exceptions.

---

## 15.4 Date functions

Minimum standard functions:

```text
IS_WORKING_DAY(Date, Scope)
NEXT_WORKING_DAY(Date, Scope)
PREVIOUS_WORKING_DAY(Date, Scope)
ADD_WORKING_DAYS(Date, N, Scope)
```

Rule:

```text
ADD_WORKING_DAYS(Date, 1)
```

means the next working day after the current date, excluding OFF days.

If an OFF day is overridden by OVERTIME at a more specific scope, it is a valid Working Day.

---

# 16. OFF_DAYS

`OFF_DAYS` is not the same as Calendar OFF.

Keep workbook business formula:

```text
OFF_DAYS = TOTAL_DAY / 7
```

Apply half-up rounding:

```text
fraction < 0.5 → round down
fraction >= 0.5 → round up
```

Examples:

```text
TOTAL_DAY = 3  → 3/7 = 0.43 → OFF_DAYS = 0
TOTAL_DAY = 4  → 4/7 = 0.57 → OFF_DAYS = 1
TOTAL_DAY = 8  → 8/7 = 1.14 → OFF_DAYS = 1
TOTAL_DAY = 11 → 11/7 = 1.57 → OFF_DAYS = 2
```

`OFF_DAYS` stays separate from actual resolved calendar days.

# 17. Multi-line Planning

## 17.1 `4 + 5 + 9`

Notation like:

```text
4 + 5 + 9
```

is a visual business representation of **dồn chuyền**:

- multiple lines sew the same planning item concurrently
- the string is presentation only
- do not use the string as the core data logic

Persist structured line assignments:

```text
PlanningRowLineAssignments
- Line 4
- Line 5
- Line 9
```

At Tổng công ty Planning level, render compactly:

```text
4 + 5 + 9
```

At Xí nghiệp / detail level, retain separate lines for monitoring:

```text
Line 4
Line 5
Line 9
```

Line detail remains available for:

- actual progress
- line capacity contribution
- operational tracking
- reconciliation

Aggregate row is presentation/roll-up, not a replacement for line-level detail.

---

## 17.2 Capacity for dồn chuyền

For multiple concurrent lines:

```text
Total Capacity
= Capacity(Line 4)
+ Capacity(Line 5)
+ Capacity(Line 9)
```

Example:

```text
Line 4 = 1,200/day
Line 5 = 1,500/day
Line 9 = 1,800/day

Total Capacity = 4,500/day
```

Planning total may use aggregated capacity.

---

# 18. Line Transfer `==>`

Notation:

```text
1 ==> 2
```

means:

- production currently runs on Line 1
- from a defined future effective date, remaining quantity is transferred to Line 2

This is an **effective-dated line assignment change**, not merely a static previous/next row relationship.

Persist structured fields:

```text
FromLine
ToLine
TransferEffectiveDate
PlannedRemainingQty
TransferStatus
```

Suggested status:

```text
PLANNED
EFFECTIVE
CANCELLED
```

Behavior:

Before effective date:

```text
item remains on FromLine
```

From effective date:

```text
remaining quantity uses ToLine
```

Destination line capacity applies from the transfer effective date.

System must check destination line availability at the effective date.

If unavailable:

```text
show Planning Warning/Error
do not auto-change transfer date
```

Do not automatically modify the plan dates just because destination capacity differs.

If an auto-calculated field would now differ from the current planning value:

- keep current planning value
- show orange `!`
- user may explicitly choose Return to Auto Calculate

# 19. Planning Versioning

## 19.1 Naming

Recommended format:

```text
2026.W26.Master.v01
```

Meaning:

```text
2026   year
W26    planning week
Master plan family
v01    major weekly planning alternative
```

Child alternative / refinement under a version:

```text
2026.W26.Master.v01.f01
2026.W26.Master.v01.f02
```

Version tree example:

```text
v01
├─ v01.f01
└─ v01.f02

v02
├─ v02.f01
└─ v02.f02

v03
```

Semantics:

```text
v = major alternative/scenario within the week
f = subordinate alternative derived from a specific v
```

---

## 19.2 Commit

`Commit` creates an immutable Planning Version.

Multiple committed versions may coexist.

Commit does not make a plan operational.

Draft Edit Sessions are not versions until committed.

---

## 19.3 Issue / Publish

Only explicit:

```text
Issue / Publish
```

makes a version operational.

When a new version is issued:

```text
Selected Version → ISSUED
Previous Issued Version → SUPERSEDED
```

Old versions remain immutable and fully auditable.

A version can be issued only if that exact version has:

```text
Recheck All Plan = PASS
```

Recheck result from parent version is not reusable for a child version.

# 21. Planning Scope

Planning Version is at **Tổng công ty level**.

Example:

```text
2026.W26.Master.v02.f01
```

represents a consolidated weekly plan for the whole company.

It is not a separate version per Xí nghiệp.

Xí nghiệp/Line detail exists inside the plan and is used for drill-down and Actual synchronization.

# 22. Actual from ERP/eGMF

Actual is synchronized from ERP/eGMF at operational detail:

```text
Xí nghiệp
→ Line
→ PO / Style / Model / Customer / Quantity / Date ...
```

Then rolled up to the correct Tổng công ty Planning row.

Example Planning row:

```text
PO001
Lines = 4 + 5 + 9
Planned Qty = 12,000
```

Actual:

```text
Line 4 = 3,200
Line 5 = 2,800
Line 9 = 3,500
```

Roll-up:

```text
Actual Qty = 9,500
Remaining Qty = 2,500
```

Drill-down must still show each source line.

---

# 23. Actual must not change issued plan

Actual only updates actual/progress layer.

Do not automatically change an Issued Planning Version:

```text
Quantity
Line
Date
Transfer
```

If Actual differs from Plan:

- warn
- highlight
- allow drill-down
- do not modify planning data

If planner wants to adjust plan based on actual, create a new `f` or `v`, then:

```text
Edit
→ Recheck
→ Commit
→ Issue
```

# 24. Mapping Tables

Do not force all value mapping into one generic business-facing table.

Use separate mapping tables per business domain where values differ between Planning and ERP/eGMF.

Examples:

```text

Customer Mapping
Sport Mapping
Factory/XN Mapping
Line Mapping
Style/CC Mapping
Model Mapping
```

Example Season:

```text
Planning: SS2025
ERP:      SS25
```

Value map:

```text
SS2025 ↔ SS25
```

Fields that are already identical may match directly without a separate value map.

Potential business fields involved in matching:

```text
FAC / XN
LINE
PO DATE
SPORT
SEASON
PO NUMBER
STYLE / CC
MODEL CODE
DESCRIPTION
CUSTOMER
```

Do not hard-code a final matching-key priority yet.

Initial rule:

- if normalized actual matches one Planning row → auto match
- if no match → warning
- if multiple possible matches → warning
- do not auto-guess

# 25. Stable integration identity

Do not treat internal eGMF database IDs as durable business keys.

eGMF internal IDs may change after:

- migration
- rebuild
- reimport
- version changes

Use stable business identity/composite business keys for cross-system mapping.

Keep source IDs only as auxiliary technical references.

Do not snapshot the entire source database.

Snapshot only what is required to explain sync/mapping results later.

Three snapshot categories:

## 30.1 Actual transaction snapshot

Keep source fields actually used for production Actual and matching.

Example:

```text

Style
Season
Customer
XN
Line

```

## 30.2 Master / mapping snapshot

For reference data used in mapping, preserve the minimum explanatory fields:

```text

SourceObject/Table
SourceKey
SourceCode
SourceName
MappedPlanningValue
MappingVersion / EffectiveDate
```

Example:

```text

```

## 30.3 Planning reference snapshot

Keep:

```text

PlanningRowId

```

so historical Actual can still explain which plan row it matched.

# 32. Year-End Carry Forward

Only unfinished items are carried into the new year.

Examples of unfinished state:

```text
production not completed
remaining production quantity > 0
active transfer not completed
PO still active
Actual still expected
tracking must continue
```

Do not copy the full old-year history into the new year.

Carry only the live state needed for continued operation.

Keep links to the old-year source record/version.

Example:

```text
2026 Planned = 20,000
2026 Actual = 17,500
Remaining = 2,500
```

New year:

```text
Opening Carry Forward Qty = 2,500
Source Year = 2026
Source Planning Row = ...
```

Suggested carry-forward states:

```text
CARRY_FORWARD_PENDING
CARRIED_FORWARD
CLOSED
```

# 34A. Authentication, Authorization & Admin

## 34A.1 Authentication

Primary authentication method:

```text
Google SSO
```

Google SSO is the default login mechanism for normal users.

Temporary fallback:

```text
Local Account Fallback
```

Local accounts are allowed only as a temporary fallback / emergency access mechanism during the initial phase or when Google SSO is unavailable.

Recommended local-account constraints:

- enabled only for explicitly authorized users
- password policy enforced
- temporary/emergency use only
- all local-account logins audited
- can be disabled later when SSO is fully stable

The authentication layer must provide a reliable authenticated `UserId` to Planning so that `EditSessionId`, audit, commit, issue, sync, and admin actions are attributable to a real user.

---

## 34A.2 Authorization Baseline

Minimum role model:

```text
Admin
Planner / Planning Editor
Viewer
```

Optional role that may initially be merged into Admin:

```text
Mapping / Sync Admin
```

Recommended baseline responsibilities:

### Admin

- manage users
- manage roles
- manage permissions
- configure Google SSO
- manage temporary local fallback accounts
- Force Unlock active Planning Edit Session
- manage Mapping masters
- manage Calendar masters
- access Audit Log
- access Sync Log
- view system/debug information

### Planner / Planning Editor

- enter Edit Mode if no other active EditSessionId exists
- edit Planning Draft
- drag/drop
- merge/split
- edit calculated overrides
- run Recheck All Plan
- Commit versions
- compare versions
- Issue/Publish only if explicitly permitted by role/permission policy

### Viewer

- view Planning
- view Issued versions
- view Actual
- view Dashboard
- view permitted logs/history
- cannot acquire EditSessionId
- cannot modify Planning

# 35. Acceptance Criteria

Implementation should be considered aligned with this design when the following are true.

## Edit Mode

- only one active `EditSessionId`
- all other users are View Only
- backend enforces session lock
- frontend works on Draft State

## Virtual Sequence

- every active draft row has valid `virtualSequence`
- sequence reindex is atomic
- UI locks during critical reindex
- reindex completes under 0.5 seconds
- sequence revision increments after successful structural change

## Undo/Redo

- 100 actions supported
- reorder / add / merge / split / edit / override can be undone
- Revert All works
- committed version is outside frontend undo history

## Formula

- formula dependency is derived from definition
- circular formulas cannot be published
- runtime has loop guard
- override uses orange `!`
- Return to Auto Calculate works
- downstream formulas use EffectiveValue

## Recheck

- Recheck scope is full plan
- commit blocked until current draft revision has successful Recheck
- edits after Recheck invalidate Recheck status
- validation panel navigates to exact row/cell

## Calendar

- Company/XN/Line hierarchy works
- smaller scope overrides larger scope
- WORKING/OFF/OVERTIME supported
- +1 Working Day skips OFF
- OFF_DAYS remains separate workbook formula

## Multi-line

- `4 + 5 + 9` is only a visual rendering
- structured line assignments exist underneath
- line details remain available
- total capacity can aggregate participating lines

## Transfer

- `1 ==> 2` has explicit effective date
- current line remains valid until effective date
- destination line availability is checked
- destination capacity applies from effective date
- system does not automatically rewrite planning dates
- changed auto result can show `!`

## Versioning

- Commit creates immutable version
- `v` = major weekly alternative
- `f` = child alternative under a specific `v`
- Issue/Publish is separate from Commit
- only Recheck-PASS version can be issued
- Compare Versions available

## Actual Sync

- actual comes from XN/Line detail
- rolls up to Tổng công ty planning row
- structured multi-line assignment is used
- Actual never mutates issued plan
- unmatched/ambiguous are warnings
- Sync Log keeps every run
- retry creates a new run

## History / Snapshot

- actual history preserved by Sync Run
- mapping/reference snapshot preserves historical explanation
- master/reference data stays online
- plan/actual history handled by year
- unfinished items carried forward before archive

---


## Authentication / Admin

- Google SSO is the primary authentication mechanism
- local account fallback exists only as temporary/emergency access
- authenticated `UserId` is available for Planning/Audit
- Admin / Planner / Viewer baseline roles exist
- backend enforces permissions independently from frontend
- Admin can manage users/roles/permissions
- Admin can configure Google SSO
- Admin can Force Unlock Planning Edit Session
- Admin can manage Mapping and Calendar masters
- Audit covers authentication and privileged/admin changes


# 36. Implementation Notes

Recommended technical principle:

> Keep business-facing configuration simple and structured, while keeping technical complexity in backend services.

Important examples:

- business user sees `4 + 5 + 9`; backend stores line assignment records
- business user sees `SS2025`; mapping table handles `SS25`
- business user edits a calculated cell; backend/frontend preserves formula + override state
- user sees `!`; system knows current value differs from active auto-calculated result
- user sees one consolidated Planning row; Actual is still traceable to individual XN/Line records

The system should remain explainable, auditable, and easy to debug.
